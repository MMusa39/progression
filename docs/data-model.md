# Data model

The schema mirrors how lifters think about a session:

> A **workout** contains an ordered list of **exercises**, and each exercise has
> an ordered list of **sets** (weight × reps).

## Entity-relationship diagram

```
app_user 1───* workout 1───* workout_exercise 1───* exercise_set
    │                              │
    │                              * 
    │                              │
    └──────────────* exercise ─────┘        (exercise: global catalog + user-created)
    │
    └──* workout_template 1───* template_exercise *───1 exercise
    │
    ├──* body_weight_entry                     (one per local day)
    ├──1 nutrition_profile                     (goal inputs)
    ├──* food (custom)      food (Open Food Facts cache, shared)
    ├──* recipe 1───* recipe_ingredient *───1 food
    ├──* food_log_entry ···> food / recipe     (nutrition snapshotted)
    └──* water_intake                          (one per local day)
```

## Design decisions

### Store the weight as entered, plus a normalized column

If we converted everything to kilograms on write, a user who logs 185 lb would
see "184.99 lb" after the round trip. We store the exact value and unit the user
typed, and let PostgreSQL maintain a **generated `weight_kg` column** that the
analytics queries use. This keeps both the display and the math correct.

### Client-generated UUIDs

Auto-increment ids need a database round trip before a row has an identity,
which breaks offline creation. UUIDs can be created on the phone, so the same
workout can be retried over and over without ever creating duplicates.

### Derived metrics are computed, not stored

The estimated 1-rep max (Epley formula: `weight × (1 + reps / 30)`), volume,
and personal records are **computed from `exercise_set` with SQL**, not stored
in their own columns. That gives the data one source of truth: editing an old
set automatically corrects every chart and PR. If the queries ever become slow,
a materialized summary table can be added without changing the API.

### Shared recipes (V8)

- **`recipe`** gains `shared` (default `false`) and `copied_from` (the friend's
  recipe a copy was saved from, `ON DELETE SET NULL`). A unique index on
  `(owner_id, copied_from)` makes "save a copy" idempotent.

### Nutrition (V7)

- **`nutrition_profile`**: one row per user: `sex`, `birth_year`, `height_cm`,
  `activity_level`, `goal_weight_kg`, `goal_date`, `adaptive`. Targets are
  computed from it on request, never stored.
- **`food`**: nutrition per 100 g (`kcal_100g`, `protein_100g`, `carbs_100g`,
  `fat_100g`, `fiber_100g`), optional `serving_g` / `serving_label`.
  `source` is `OPEN_FOOD_FACTS` (cached product, `owner_id` NULL, unique
  barcode) or `CUSTOM` (`owner_id` set; a check constraint ties the two together).
- **`recipe`** (client-generated id) and **`recipe_ingredient`** (`position`,
  `food_id`, `grams`). Per-serving nutrition is derived from the ingredients.
- **`food_log_entry`**: `logged_on` (the user's local date), `meal`, `kind`
  (`FOOD` / `RECIPE` / `QUICK`), `amount` + `amount_unit` (`G` / `SERVING`),
  `name` and the **nutrition snapshot** (`kcal`, `protein_g`, ...). `food_id` /
  `recipe_id` are kept for re-logging but set to NULL if the source is
  deleted; the entry itself never changes. See ADR 0010.
- **`water_intake`**: `(user_id, logged_on)` → `ml`.

### Body weight (V6)

- **`body_weight_entry`**: primary key `(user_id, measured_on)`, so there's one
  weigh-in per local calendar day and re-logging replaces it. `weight` +
  `weight_unit` as entered, plus a generated `weight_kg`, the same pattern as
  `exercise_set`. The trend line is computed in Java (`WeightTrend`), not stored.

### Push notifications (V5)

- **`push_token`**: `token` (primary key), `user_id`, `platform`, `created_at`,
  `last_seen_at`. The token is the key because a phone belongs to whoever
  signed in on it last: registering an existing token reassigns it.
  Tokens Expo reports as `DeviceNotRegistered` are deleted.
- **`app_user`** gains `notify_friend_requests` and `notify_friend_prs` (default `true`).

### Friends (V4)

- **`app_user`** gains `username` (unique, lowercase, `^[a-z0-9_.]{3,20}$`),
  `share_workouts` (default `true`) and `invite_code` (unique, nullable until
  first requested).
- **`friendship`**: `requester_id`, `addressee_id`, `status` (`PENDING` /
  `ACCEPTED`), `created_at`, `accepted_at`. A unique index on
  `(LEAST(requester_id, addressee_id), GREATEST(requester_id, addressee_id))`
  allows **one row per pair** regardless of who asked whom, so "A→B" and
  "B→A" can't both exist.

### Analytics building blocks (V3)

- **`estimated_one_rep_max(weight_kg, reps)`**: an immutable SQL function
  implementing the Epley formula (a single rep is returned as-is). Defining it
  once in the database guarantees that charts, records and summaries all agree.
- **`working_set` view**: completed, non-warm-up sets with at least one rep,
  joined to their workout (user, start time) and exercise, plus `volume_kg`
  and `e1rm_kg`. Every stats query reads from this view. PostgreSQL inlines simple
  views, so the underlying indexes are still used.

Weeks for the training streak are computed with
`date_trunc('week', started_at AT TIME ZONE :tz)`, so a workout on Sunday
night counts toward the week the *user* experienced, not the UTC week.
Recent personal records use a window function: each session's best is compared
with `max(...) OVER (PARTITION BY exercise ORDER BY started_at ROWS BETWEEN
UNBOUNDED PRECEDING AND 1 PRECEDING)`, the best of all *earlier* sessions.

### Indexes

| Index | Supports |
| --- | --- |
| `workout (user_id, started_at desc)` | History list, newest first |
| `workout_exercise (exercise_id, workout_id)` | "Last time you did this exercise" and progression charts |
| `exercise (owner_id, lower(name))` unique | Case-insensitive name uniqueness and search |
